# ExeFS `.code` 内のフィールド/エンカウント関連構造

対象: `.code.decompressed.bin`（3DS ExeFS実行コード、ARM 32bit固定長命令）。
アドレスはベースゲームのvirtual address（`FuncSearch.txt`記載値）。
ファイルオフセット = VA − 0x100000。

## RomFSファイルマニフェストテーブル

`.code`内に、`LEVELDATA/`配下の`.dat`ファイルパスへのポインタを列挙する
テーブルが埋め込まれている。

- 先頭VA: `0x3ee930`
- エントリサイズ: 40byte、アルファベット順で51件
- 各エントリの`+12`にパス文字列へのポインタ
- 実行時のリソースロード自体はこのテーブルを直接参照しているわけではなく
  （ログ/登録用の文字列表である可能性が高い）、別経路でファイルがロードされる

## `dq7_field_symbol.dat`（159レコード×20byte）

世界地図（`wld_*`マップ）の徘徊シンボル専用のアンカー座標テーブル
（ダンジョン内シンボルはここに含まれない）。

```
+0x00 u8   id (= レコード番号 - 1)
+0x01-03   FF FF FF（固定マーカー）
+0x04 f32  X 座標（世界地図タイル座標、範囲 0〜176）
+0x08 f32  Y 座標
+0x0c u16  mapId（dq7_encount_tile.dat / dq7_floor_list.dat の +0x04 と一致）
+0x0e u16  symId（シンボル個体の一意ID。隣接サブ領域をまたぐ個体のみ共有）
+0x10 u32  予約（通常0。1レコードのみ 0x5a2 の例外値を確認）
```

索敵半径・追跡半径に相当するフィールドはこのテーブルには存在しない（座標+ID系のみ）。

## `Encount`クラス: 歩数カウンタ方式のエンカウント判定

`Encount::execWalk`（VA `0x228818`）が1マス移動ごとに呼ばれる判定本体。

フィールドレイアウト（オフセットはthisからの相対）:
- `+0x00` u16: `stepThreshold`（歩数カウンタの折り返し値）
- `+0x05` u8: terrain/zone種別パラメータ（フィールド=0、ダンジョン=8）
- `+0x14` u8: 判定ステート（0→1→2と進行し、2到達で最終確定）
- `+0x18` u16: `stepCounter16`（1マス移動ごとに+1、`stepThreshold`到達でリセット）
- `+0x1a` u16: `totalSteps16`（歩数の累計、用途未確認）
- `+0x1c` u8: エンカウント成立フラグ（ステート2到達時に`Encount::brew`が真を返すと1）
- `+0x5c`: `EncountCountDown`のインスタンス（下記）

`stepThreshold`は`Encount::setupField`（VA `0x1877fc`）/
`Encount::setupDungeon`（VA `0xa6f24`）の両方で即値`8`固定として初期化される
（RomFSデータ由来ではなく、コード内に直接埋め込まれた定数）。
`Encount::setupDungeon`では同じ即値ロードがterrain種別`+0x05`にも使われている
（両フィールドが同じ命令で同時に初期化される実装になっている）。

### `EncountCountDown`

- `EncountCountDown::setupRandom`（VA `0x198390`）/`EncountCountDown::exec`
  （VA `0x1984f4`）がカウントダウン減算を担当
- `EncountCountDown::setupSymbol`（別名`fcn.001503cc`、VA `0x2503cc`）が
  「折り返しごとの実際の間隔」を決定する。rodataに埋め込まれた重み付き抽選
  カーブテーブル（VA `0x402470`〜`0x402528`付近の整数配列）と、
  `rand(0..31)`を使い累積分布から値を引く。terrain種別`+0x05`が`8`
  （ダンジョン）かどうかで参照テーブルを切り替える
- 上記カーブテーブル・`stepThreshold`とも RomFS データを一切参照しない
  （頻度の一次パラメータはすべてExeFS内の固定値）

## `SymbolEncountStatus`: グリッドベースの湧き位置決定

同名クラスが2つの異なるVA帯（`0x21bxxx`台と`0x33exxx`台）に存在する
（役割の違いは未確定）。

### グリッドセルフラグ（u16/セル）

- `0x8000`: セルが別シンボルに占有中
- `0x2000`: 今回の探索で訪問済み
- `0x4000`: セットされていると「連結成分が5マス以上の開けた地形」判定の
  対象になる（`isCellRootPos`参照、後述）
- 下位ビット（`& 0x3f`）: タイル種別（値`1`/`2`は候補から除外される禁止タイル）
- 上位nibble（`>> 28`）: 優先度（`calcEncountPos`の候補選択で使用）

グリッド構造体（シングルトン経由 `[0x5c7234]→+8→+0x10000→+0x34` 相当）:
- `info->+0x10`: 1リングあたりの実距離スケール（`ringDistScale`）
- `info->+0x18`/`+0x1c`: セル分割に使うfloat除数（セルサイズ、マップごとに
  異なる可能性が高い。出どころ未確定）
- `info->+0x1c`: グリッド幅（セル数）
- `info->+0x20`: グリッド高さ（セル数）

### `SymbolEncountStatus::registEncountData`（VA `0x229844`）

16スロット×84byte(0x54)の固定配列から空きスロット（`+0x04`が`-1`）を探し
初期化する。レコードフィールド（一部、詳細未解析分あり）:
- `+0x00`: 呼び出し元が渡した引数（シンボル/エンカウントID）
- `+0x04`: 別テーブルの`+0x1a`バイト（モンスターデータ関連と推定）
- `+0x08`: グローバルカウンタ値
- `+0x1c`/`+0xc`: パーティ4人分のステータス値配列（詳細未確認）

### 湧き位置決定の優先順位（確定した制御フロー）

```
1. isCellRootPos(pos, maxRadius)
     0x4000フラグが立ったセルを起点に、連結した0x4000セルが
     5マス以上あるかを判定するフラッドフィル。成功すればそこで即確定。
     （「町の入口専用アンカー」という仮説は検証の結果否定され、
     「ある程度広い開けた地形」を表す汎用フラグと考えられる）
2. ①が失敗 → calcEncountPos(pos, maxRadius)
     半径インデックス ring を初期値から1ずつ増やしながら、そのリング上の
     4候補点を試す貪欲法。ループ条件は `ring * cellSize < maxRadius`。
     いずれかの候補が「未占有・禁止タイルでない・優先度が基準以上」を
     満たした時点で、それ以上遠いリングを探さずその場で確定する。
     `maxRadius`はフィールド/ダンジョン共通の固定float定数
     （リテラルプール上の値、マップ種別による分岐は無い）。
3. ①②とも失敗 & リトライ可 → calcNearPos(pos)
     中心セルからの4方向BFS（上下左右）。ラウンド上限10、1ラウンドごとに
     frontier全方向へ1マス拡張。「占有中/訪問済み」以外の除外ロジックは
     持たない（近さによる除外は無い）。最大200件の候補を収集。
```

`calcEncountPos`/`isCellRootPos`/`calcNearPos`はいずれもバイナリ全体で
唯一の呼び出し元（単一の共有関数）から呼ばれており、フィールド/ダンジョンで
個別の初期化分岐は存在しない。

`SymbolEncountStatus::isToheros`（VA `0x2299e4`）:
```
monsterLevelOrRank <= playerLevel - 5 を満たせば真を返す
（トヘロス等のグローバル状態が有効な場合にのみ判定される）
```
しきい値`5`はコード側に直接埋め込まれた即値。

## モンスターの移動ロジック（`EnemyObjectFlow`/`TaskEnemyObject`）

`CharacterObject`を継承すると見られるモンスター専用オブジェクト
（`PeopleParty::add`→汎用ファクトリ`fcn.0x193148`経由で32要素プールから
確保される）の`+0x10`フィールドが、確認できた3種類の移動ロジック全てで
共通して参照される移動速度スカラー（f32）である。

確認済みの移動ステート（`EnemyObjectFlow`領域、VA `0x1df908`〜`0x1e2604`付近）:

1. **直接追跡**: プレイヤーの現在位置へ毎フレーム直接ベクトルを再計算して接近。
   タイマー`+0x5c`が閾値7未満の間は待機、12以上で接近開始。
2. **徘徊**: 現在地の8方向から通行可能な候補点を順に試し、見つかった点へ
   ノード補間で移動。
3. **突進（予測移動）**: プレイヤーの現在速度×予測時間定数でプレイヤーの
   将来位置を推定し、その1点に向けて直進する「偏差撃ち」型の移動。

いずれも実際の移動は「行動ノード」生成関数`fcn.0x18fae4(nodeType, targetObj)`
経由で構築される、種別ID方式のビヘイビアツリーシステムに乗っている
（ノード種別0 = 補間移動系）。ノード種別ディスパッチの全体像・各パラメータの
意味は未解読。

モンスター種別ごとに異なるコードパスがあるわけではなく、全モンスター共通の
1つの状態機械実装で、個体差は参照する数値（速度・タイマー閾値等）側に
現れる設計になっている。速度フィールド`+0x10`の書き込み元（RomFSデータ由来か
固定値か）は未確定。
