# フィールドカメラ・エンカウントデータ(`LEVELDATA/`)仕様

RomFS内`LEVELDATA/`フォルダに格納される、フィールドカメラ・エンカウント関連の
データテーブル群。いずれも実機での動作確認・既存ツールとのクロスリファレンスで
構造が確定済みの範囲のみ記載する(未確定箇所はその旨明記)。

## 共通コンテナヘッダ

`LEVELDATA/`配下の多くのファイルは共通の16byteヘッダを持つ:

```
0x00-0x03: マジック/ハッシュ (4byte, ファイル内容依存で変化)
0x04-0x07: レコード数 (int32)
0x08-0x0B: レコードサイズ (int32)
0x0C-0x0F: レコード数 (int32, 0x04-0x07と同値)
0x10-    : レコード配列
```

## `dq7_camera_param.dat`(12レコード×36byte) — フィールド探索カメラの実体

実機検証により、フィールド探索中のカメラに実際に使われているテーブルであることが
確定している(`dq7_map_camera.dat`・`dq7_look_down_camera.dat`は通常のフィールド
探索カメラには使われていないことを実機で確認済み)。

```
+0x00: id (下位byteがID, 値0-9, 100, 101)
+0x04: pos.yaw   (float, 度数)  — カメラの水平回転角
+0x08: pos.pitch (float, 度数)  — カメラの見下ろし角(大きいほど真上に近づく)
+0x0C: pos.dist  (float)        — カメラとプレイヤーの距離(極座標の動径成分)
+0x10: target.x  (float, 未検証) — 注視点オフセット(プレイヤーからの相対位置と推測)
+0x14: target.y  (float, 未検証)
+0x18: target.z  (float, 未検証)
+0x1C: near clip (float, 推定)  — 値を大きくしすぎると手前の地形がクリップされ画面が暗転する
+0x20: far clip  (float, 推定)  — 値を小さくすると遠景の描画範囲が狭くなる
```

`pos`フィールドは直交座標ではなく**(ヨー角, ピッチ角, 距離)の極座標**であることが
実機検証で確定している(3成分とも等倍しても角度構成は変化せず、距離成分のみの
変更で純粋に遠近だけが変わる)。

### `dq7_map_camera.dat`(220レコード×52byte)

カメラプリセットのデータ。`dq7_camera_param.dat`と同系統のレイアウト
(id + pos.xyz + target.xyz + 距離/FOV関連値 + 未解読領域)を持つが、**実機の
通常フィールド探索カメラには使われていないことが確認済み**(全レコード一括の
極端な値変更でも見た目の変化なし)。用途未確定。

## マップコード → フロアパラメータの連結

```
MAP/_list.txt (行番号 = マップの通し番号)
     │  同じ通し番号
     ▼
LEVELDATA/dq7_floor_list.dat (同インデックスでマップコード名を保持、可変長文字列レコード)
     │  同じインデックス
     ▼
LEVELDATA/dq7_floor_param.dat (同インデックスで int32×3 を保持、12byte/レコード)
```

`dq7_floor_param.dat`も他のLEVELDATAの表と同じく20byteのヘッダを持ち、レコードは
ファイル先頭0x14から始まる(`ExcelBinaryData::getRecordDynamic`)。
**レコード+0x04(u8)はそのフロアのBGM番号**(dsno)。マップに入ったとき
`DQSoundManager::playTownBgm`がこの番号で実行コード内のBGM表
(dsno → `SOUND/dq7_sound_data.bcsar`のサウンド)を引く。
例: `m01nout` 5(`DQ7_BGM_M06_NODOKA`)、`c01nout` 4(`M05_HORN`)、
`wld_n01a` 12(`M13_FIELDS_NOW`)。コード内の表のBGM部分は34件
(dsno 0-33、32と33は空き)。

(訂正: このバイトは以前、16byteヘッダとして数えて「3番目のint32の下位1byte =
`dq7_map_camera.dat`のインデックス」と書いていた。BGM番号である。)

## `dq7_encount_data.dat`(304レコード×56byte) — エンカウント本体

### ファイル全体

- 20byteヘッダ(nrec=304, recsize=56)。レコードiはファイル先頭0x14 + i×56から
  (`EncountData::setupData`がそこから読む。それが解釈する欄は下表に注記)。
- レコード0は全ゼロ(ダミー/番兵)。レコード番号が戦闘番号
  (`Encount::brew` → `EncountData::setup(戦闘番号)`。スクリプトの戦闘命令が渡す)。
- 実データを持つレコードは167件。残り137件は「モンスター無し枠」。

### レコード構造(オフセットはレコード先頭から)

| off | 型 | 内容 |
|---|---|---|
| +0x00 | u16 | 自己インデックス(配列上の位置と完全一致) |
| +0x02 | u16×5 | arrayA: モンスターIDロスター。0=空きスロット、重複なし、概ね昇順 |
| +0x0c | u16×4 | arrayB: 実フォーメーション(実際に出る4枠)。重複可。arrayAの部分集合とは限らない |
| +0x14 | u16×2 | スロット11・12(他の枠と同じく読まれる。スロット順では+0x18の後)。全レコードで0 |
| +0x18 | u16 | 「レア客」枠。低確率で編成に加わる1体。重み(下記ブロック1)がスロット中最低になりやすく、メタル系・格上モンスターが置かれやすい |
| +0x1a | u8 | 逃走(引き逃げ)判定レベル閾値。プレイヤーレベルがこの値を超えると敵が逃走する。モンスターありレコードは中央値≈33、空きレコード・ボス戦は99が多い |
| +0x1b | u8 | **戦闘BGM番号**(dsno。`EncountData::setupData` → Encount+0xc4 → `DQSoundManager::playBattleBgm`)。16 `DQ7_BGM_M17_FIGHT`(212件)、17 `M18_STRONGERS`(ボス、63件)、30 `M35_ORUGODEMIRA`(6件)、0(23件) |
| +0x1c | u8×8 | mid: フォーメーション(出現数・隊列)の重み付き抽選表。`roll=rand(1..mid[7])`、最初に`roll<=mid[i]`となるiがテンプレ番号。テンプレi0=敵1体。値を小さくするほど小編成に寄る |
| +0x24 | u8 | ゾーン固有の調整値(範囲11-41、釣鐘型分布)。実機検証でエンカウント頻度には影響しないことを確認済み。用途未確定 |
| +0x25 | u8 | 特殊エンカウント番号(`EncountSpecial::setup`。編成の抽選でテンプレ12が出たときに使う)。ほとんど0 |
| +0x26 | u8 | bit0-2: 3つのフラグ、bit5-7: 3bitの値(`setupData`)。ほぼ全件96(0x60) |
| +0x27 | u8 | bit0-2とbit3-5: `EncountData::setup`の3択の抽選の重み2つ(残り1つは+0x28のbit0-2) |
| +0x28 | u8 | bit0-2: その抽選の3つ目の重み。bit3-5: 3bitの値(`setupData`) |
| +0x29-0x2e | 6byte=12ニブル | ブロック1: スロット別「出現重み」表。下位ニブル先で読み、ニブルが`[A0,A1,A2,A3,A4, B0,B1,B2,B3, +0x18, +0x14, +0x16]`に1対1対応(`EncountData::setup`がこれで枠を抽選する)。空きスロットは必ず重み0、埋まったスロットは必ず重み1-9。メタル系スロットは平均的に低い重みを持つ。+0x2e(最後の2枠)はほぼ全件0 |
| +0x2f-0x34 | 6byte=12ニブル | ブロック2: ブロック1と同じスロット対応の表(下位ニブル先、空きスロット=0)。`setupData`が1つずつ`btl::getAppearCount`に通す(数) |
| +0x35-0x37 | 3byte | ほぼ全レコードで`FF FF FF` |

(訂正: この表の以前の版は16byteヘッダとしてレコードを数えていたため、全オフセットが
4大きかった。「+0x00のマーカー`00 FF FF FF`」は前のレコードの末尾、「予約」の+0x18 u16×2はスロット11・12で、
「+0x1fはほぼ16固定」の定数は上の戦闘BGM番号である。)

特殊値: arrayAに991-999が入るレコード(12件)は通常のモンスターID範囲外の特殊コード
(すれちがい通信・石版固定戦闘・モンスターパーク等、スクリプト側から差し込まれる
枠と推測)。

### マップ→レコードの対応

```
フロアID (例: 1720 = d07pf3)
     │  dq7_encount_tile.dat (+0x00) で検索
     ▼
+0x04 / +0x05 / +0x06 のバイト(物語の段階別。下記) = レコード番号そのもの
     ▼
dq7_encount_data.dat レコード #n
```

(訂正: この文書の以前の版は、このバイトを「ゾーンID Z」と読み、1つのマップの南側/北側で
レコード`2Z`/`2Z+1`を使い分けると書いていた。これは誤り。`EncountTile::getTileId`が
バイトを返し、`Encount::setupDungeon`/`EncountData::setup`はそれをそのままレコード番号として
使う。「聖風の谷の南と北」とされた#76/#77は別々のマップのもので、`wld_p17a`/`wld_p17b`が76、
`wld_p17c`が77を使う。1つのマップが使うレコードは物語の段階ごとに1つ。)

マップに入ると`TownTriggerTaskSystem::initialize`がフロアのレコードを読む。0でなければ、
その値を`SymbolEncountStatus+0x750`(`registEncountData`がすべての戦闘に渡すレコード)に入れ、
エンカウントのタスク(`TaskEnemyEncount`)を始める。0ならそのフロアにエンカウントは無い。

### `dq7_encount_tile.dat`(747レコード×28byte)

行はファイル先頭0x14から(20byteヘッダ)。

| off | 内容 |
|---|---|
| +0x00 | u32 フロアID(`dq7_floor_list.dat`) |
| +0x04 | u8 type0フラグ1740が立っていない間のレコード |
| +0x05 | u8 フラグ1740が立った後(フラグ2000が立っていない間)のレコード |
| +0x06 | u8 フラグ2000が立った後のレコード |
| +0x07〜 | 部屋コード文字列(ASCII、NUL終端)。例: `d07pf3`=ダンジョン07・過去(`p`)・3階。行の最後のバイトは0xFF |

(訂正: 以前の表は16byteヘッダとして数えていたため、全オフセットが4大きかった。
「+0x04 u16 部屋固有ID」はフロアIDの下位16bit、「+0x08/+0x09/+0x0a」は上の+0x04/+0x05/+0x06。)

### `dq7_encount_tile_sea_chapter4.dat` / `dq7_encount_tile_sea.dat`(16行×32byte)

16行(ブロックz)×16個のu16レコード番号(ブロックx)。全体マップ(`wld_n25a`、フロア5161)で
船に乗っている間、`TaskEnemyEncount::execute`が両軸とも`clamp(int((pos + 160) * 16 / 320), 0, 15)`
でブロックを求める。`EncountTile::setupField`はそのブロックの値を
`dq7_encount_tile_sea_chapter4.dat`から読む。海のエンカウントは歩数によるランダム
エンカウント(シンボル無し)。

`dq7_encount_tile_sea.dat`も同じ形で、起動時に読み込まれる(`DQ7EncountTileSea::setup`)が、
読むコードは無い。

### ランダム(歩数)エンカウント

`TaskEnemyEncount::execute`には、歩数を数え(`Encount::execWalk`)、シンボルを出さずに
直接戦闘を始める(`SymbolEncountStatus::registEncountData`)枝がある。この枝を通るのは、
全体マップの海の上、フロア3538/3541(`x09nin3f1a`/`x09nin3f1c`)、地域122
(`d24nin1`〜`d24nin4`)。ほかのフロアはシンボルを使う。シンボルの位置は
COLLの`CELL`格子で決まる(`SymbolEncountStatus::calcEncountPos`とその周りの関数)。

### `dq7_world_atlas_offset_large.dat`(40byte行) — 下画面の拡大地図

| off | 内容 |
|---|---|
| +0x00 | u32 フロアID |
| +0x04 | u32 type0フラグ: このフラグが立っていない間、この行を使う(0=常に) |
| +0x08 / +0x0c | s32 画像の左上の位置(「拡大地図の画素」でのx/y) |
| +0x10 | 画像名(24byte): `/SCREENTEX/atlas/world_l/<名前>.fpt.lz` |

`WorldAtlasLarge::canOpen`/`load`は、今のフロアの行のうちフラグが立っていない最初の行を使う。
ただし画像が存在する場合に限る。画像は64×64のRGBA8タイル`texNNN.dmp`と`size.dat`を
まとめた`.fpt.lz`(FPT0)。画像上のプレイヤーの画素
(`WorldAtlasLarge::convertFloorPosToAtlasPos`)は
`int((V * 10 + 1600) * 0.6496875) - (+0x08, +0x0c)`。Vは
`WorldAtlasStatus::convertWalkPosToVehiclePos`が求める全体マップ上の位置で、フロアの
`dq7_world_atlas_offset.dat`の行を使って`(+0x10 + x * +0x18, -+0x14 + z * +0x18)`となる。
画像は320×240の下画面に1:1で描かれ、プレイヤーが中央に来るようにスクロールする。

### `dq7_field_symbol.dat`(159レコード×20byte) — 世界地図専用の徘徊シンボル表

```
+0x00 u8  id (= レコード番号-1)
+0x01-03  FF FF FF
+0x04 f32 X (世界地図座標)
+0x08 f32 Y (世界地図座標)
+0x0c u16 mapId (フロアID: dq7_encount_tile.dat +0x00 / dq7_floor_list.dat と一致。例外なく世界地図`wld_*`系の行)
+0x0e u16 symId (シンボル個体の一意ID。隣接サブ領域をまたぐ個体のみ同じ値を共有)
+0x10 u32 (ほぼ常に0)
```

このテーブルは**世界地図のシンボルのみ**を対象とする。ダンジョン等の屋内マップの
シンボルはこの表に含まれず、その湧き位置はExeFS側(実行コード)で制御されている。

### `dq7_encount_pattern.dat`(145レコード×4byte)

3レコード周期の`[id, 3byteビットマスク]`構造。マスクのpopcountがidの増加とともに
広がっていく分布を持つ(確率カーブ、または有効スロットのビットフィールドと推測)。
詳細な意味は未確定。

## エンカウント発生頻度の制御箇所について

`dq7_encount_data.dat`(+0x1e, +0x28, テール領域)・`dq7_ai_param.dat`(174レコード×
48byte、+0x24-0x28)・`dq7_floor_param.dat`(+0x04。旧来の16byteヘッダ読みのオフセット)の各フィールドを実機で変更検証
した範囲では、**フィールド上のシンボル湧き頻度・エンカウント発生頻度そのものを
制御するフィールドはRomFS側データには見つかっていない**。発生頻度の制御は
ExeFS側の実行コードにあると考えられる。

## 付録: `dq7_item_list.dat`(670レコード×52byte) — 装備効果パラメータ

エンカウント抑止アイテムの効果を辿る過程で判明した、アイテムデータの構造。

| off | 型 | 内容 |
|---|---|---|
| +0x00 | u16 | タイプ/フラグ |
| +0x08 | u16 | 名前文字列ID |
| +0x0c | u32 | 使用効果リソース/メッセージ雛形へのポインタ(消耗品は少数のリソースを共用) |
| +0x10 | u16 | 買値(0=非売品) |
| +0x14 | u16 | 売値 |
| +0x16 | u16 | 説明文テキストID |
| +0x1a | u16 | 効果ID/カタログID(素の装備は0、それ以外はほぼアイテムごとに一意) |
| +0x1c | u16 | 効果パラメータ |
| +0x20 | u8 | アイテムID(=レコード番号) |
| +0x22 | s16 | `+0x2c`が指すパラメータへの加算値(武器=攻撃力、防具=守備力等) |
| +0x24 | s16 | 補正値(多くは+0x22と同値。武器では負値のことがあり命中/会心または両手持ちペナルティと推測) |
| +0x28 | u8 | 追加ステータス(各種耐性等) |
| +0x2c | u8 | 効果対象パラメータ種別(実機確認済み: 1=攻撃力 2=守備力 3=すばやさ 4=かしこさ。他に5=運勢系アクセサリ、6=消耗品、7=その他消耗品、8=重要/イベント/未分類、9=石/特殊、0=効果なし。1-4はステータスメニューの並びと一致) |
| +0x2d | u8 | 装備スロット/小分類(1=武器 2=体防具 3=頭 4=脚系 5=アクセサリ 6=消耗品 7=カギ 9/11=重要 12=石) |
| +0x33 | u8 | ショップ系ビットフィールド(売買可否等) |

`dq7_apprise_item.dat`(664レコード×40byte)は純粋な説明文/テキストポインタ表で、
効果の種類に関する情報は持たない。アイテムの実際の効果(エンカウント抑止等)は
RomFSデータには記述がなく、ExeFS側が効果ID(`+0x1a`)またはアイテムIDで
ディスパッチしていると考えられる。
